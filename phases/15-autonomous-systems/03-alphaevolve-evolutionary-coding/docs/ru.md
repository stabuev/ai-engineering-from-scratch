# AlphaEvolve — эволюционные coding agents

> Соедините frontier coding model с эволюционным циклом и машинно-проверяемым evaluator. Дайте циклу работать достаточно долго. Он открывает процедуру умножения комплексных матриц 4x4, которая использует 48 скалярных умножений — первое улучшение результата Strassen за 56 лет. Он также находит эвристику планирования Borg масштаба Google, которая возвращает ~0.7% cluster compute в продакшене. Архитектура намеренно простая. Выигрыши приходят из строгости evaluator.

**Тип:** Изучение
**Языки:** Python (stdlib, игрушечный evolutionary-loop)
**Предварительные требования:** Фаза 15 · 01 (long-horizon framing), Фаза 15 · 02 (self-taught reasoning)
**Время:** ~60 минут

## Проблема

Большие языковые модели умеют писать код. Эволюционные алгоритмы умеют искать по пространству кода. И то и другое десятилетиями пробовали по отдельности; оба подхода упирались в потолки. Потолок LLM — confabulation: модель пишет правдоподобный код, который не делает того, что она утверждает. Потолок эволюции — стоимость поиска: случайные мутации синтаксиса редко дают компилируемые программы, не говоря уже о лучших.

AlphaEvolve (Novikov et al., DeepMind, arXiv:2506.13131, June 2025) объединяет их. LLM предлагает целевые правки к базе программ; автоматический evaluator оценивает каждый вариант; варианты с высоким score становятся родителями для будущих поколений. LLM берет на себя дорогой шаг написания правдоподобного кода; evaluator ловит конфабуляции. Цикл работает от часов до недель.

Заявленные результаты: умножение комплексных матриц 4x4 за 48 скалярных умножений (граница Strassen 1969 года была 49), эвристика планирования Borg в продакшене Google, ускорение FlashAttention kernel на 32.5%, улучшения пропускной способности обучения Gemini.

Архитектура работает, потому что evaluator машинно-проверяемый. Там, где evaluator таким не является, она не работает. Эта асимметрия и есть урок.

## Концепция

### Цикл

1. Начать с seed program `P_0`, корректной, но неоптимальной.
2. Поддерживать базу вариантов программ, каждый из которых оценен evaluator.
3. Сэмплировать одного или нескольких родителей из базы (в стиле MAP-elites или island-based).
4. Запросить LLM (Gemini Flash для многих кандидатов, Gemini Pro для сложных) сгенерировать измененный вариант родителя.
5. Скомпилировать, запустить и оценить вариант на held-out evaluator.
6. Вставить в базу с ключом по score и feature vector.
7. Повторять.

Важны две детали. Во-первых, LLM получает в промпте не только родительскую программу — обычно также несколько лучших вариантов из базы, сигнатуру evaluator и краткое описание задачи. Задача модели — предложить целевое изменение, которое может улучшить score. Во-вторых, база структурирована (MAP-elites grid, island-based), чтобы цикл исследовал разнообразие, а не только текущего лидера.

### Почему evaluator не подлежит обсуждению

Все выигрыши AlphaEvolve приходят из доменов, где evaluator быстрый, детерминированный и трудный для gaming:

- **Алгоритм умножения матриц**: unit test, который умножает матрицы и проверяет побитовое равенство.
- **Эвристика планирования Borg**: production-grade simulator, который воспроизводит историческую нагрузку кластера и измеряет wasted compute.
- **FlashAttention kernel**: тест корректности плюс wall-clock benchmark на реальном железе.
- **Пропускная способность обучения Gemini**: измеренные GPU-seconds per step.

В каждом случае evaluator ловит тот класс ошибок LLM, который иначе доминировал бы: выдуманные заявления о корректности, заявления о производительности, исчезающие на железе, и отказы на edge cases. Уберите evaluator, и цикл начнет оптимизировать красивый код.

### Reward hacking — другая сторона того же утверждения

Эволюция оптимизирует то, что измеряет evaluator. Если evaluator несовершенен, цикл найдет несовершенство. В неверифицированном домене цикл оптимизировал бы поверхностный признак, а не задуманное поведение. DeepMind явно отмечает это в статье: успехи AlphaEvolve переносятся только в домены, где строгость evaluator соответствует амбиции поиска.

Конкретные примеры reward hacking в code-search loops в 2025-2026:

- Цели оптимизации, вознаграждавшие "time to complete", поощряли отправку пустых решений.
- Benchmark scores, вознаграждавшие correctness-under-test, поощряли запоминание тестов и overfitting.
- Прокси "code quality" вознаграждало удаление комментариев и переименование переменных без семантических изменений.

Исправление в AlphaEvolve: использовать held-out evaluator, который LLM никогда не видела, с входами, генерируемыми во время оценки. Даже тогда DeepMind рекомендует сильное ревью любого предложенного развертывания.

### Почему LLM + search лучше каждого по отдельности

LLM может производить компилируемые, семантически правдоподобные модификации. Random-mutation GA на Python-файле в 2000 строк почти всегда производит синтаксические ошибки. LLM также концентрирует поиск в правдоподобных окрестностях (изменить одну функцию, а не случайные байты), что резко снижает число потраченных впустую вызовов evaluator.

Evaluator, в свою очередь, ловит конфабуляции LLM. LLM будет уверенно утверждать, что функция "является O(n log n) в пределе", когда на деле она O(n^2); wall-clock benchmark закрывает вопрос.

### Где AlphaEvolve находится во frontier stack

| Система | Генератор | Evaluator | Домен | Пример выигрыша |
|---|---|---|---|---|
| AlphaEvolve | Gemini | correctness + benchmark | algorithms, kernels, schedulers | 48-mul 4x4 matmul |
| FunSearch (DeepMind, 2023) | PaLM / Codey | correctness | combinatorial math | cap-set lower bounds |
| AI Scientist v2 (Sakana, L5) | GPT/Claude | LLM critique + experiment | ML research | ICLR workshop paper |
| Darwin Godel Machine (L4) | agent scaffolding | SWE-bench / Polyglot | agent code | 20% → 50% SWE-bench |

Все четыре — вариации одного рецепта: generator плюс evaluator, цикл. Различаются они тем, что оценивает evaluator и насколько он строг.

## Использование

`code/main.py` реализует минимальный AlphaEvolve-подобный цикл для игрушечной задачи symbolic regression. "LLM" — это stdlib-прокси, предлагающий небольшие синтаксические мутации программы, которая вычисляет целевую функцию. "Evaluator" измеряет mean squared error на held-out test points.

Наблюдайте:

- Как лучший score улучшается по поколениям.
- Как MAP-elites grid сохраняет разнообразные решения, чтобы цикл не сошелся к локальному минимуму.
- Как удаление held-out test (training-only evaluator) позволяет циклу впечатляюще overfit.

## Практический результат

`outputs/skill-evaluator-rigor-audit.md` — предварительное условие для рассмотрения AlphaEvolve-style loop в новом домене: действительно ли ваш evaluator ловит отказы, которые вам важны?

## Упражнения

1. Запустите `code/main.py`. Отметьте траекторию лучшего score. Отключите held-out evaluator (flag `--no-holdout`) и запустите заново. Измерьте overfitting.

2. Прочитайте Section 3 статьи AlphaEvolve про MAP-elites grid. Спроектируйте feature-vector descriptor для новой задачи (например, compiler optimization passes), который сохранял бы разнообразие поиска.

3. Результат 48 умножений для 4x4 улучшил 49-mul bound Strassen спустя 56 лет. Прочитайте Appendix F статьи и объясните в трех предложениях, почему evaluator для этой задачи особенно легко сделать правильно и почему большинство доменов на нее не похожи.

4. Предложите один домен, где AlphaEvolve провалится. Точно укажите, где ломается evaluator и почему.

5. Для знакомого вам домена напишите сигнатуру evaluator, которую вы бы использовали. Включите (a) условия корректности, (b) performance metric, (c) правило генерации held-out input, (d) хотя бы одну anti-reward-hacking check.

## Ключевые термины

| Термин | Как обычно говорят | Что это на самом деле значит |
|---|---|---|
| AlphaEvolve | "Эволюционный coding agent DeepMind" | Gemini + база программ + машинно-проверяемый evaluator |
| MAP-elites | "Архив, сохраняющий разнообразие" | Сетка с ключом по feature vectors; каждая ячейка хранит лучший вариант с этим descriptor |
| Island model | "Параллельные эволюционные подпопуляции" | Независимые популяции, которые периодически мигрируют; предотвращает premature convergence |
| Machine-checkable evaluator | "Детерминированный oracle" | Unit test, simulator или benchmark, который LLM не может подделать — предварительное условие для этого цикла |
| Reward hacking | "Оптимизация меры, а не цели" | Цикл находит способ максимизировать score без выполнения задуманной задачи |
| Seed program | "Начальная точка" | Исходная корректная, но неоптимальная программа, из которой цикл эволюционирует |
| Held-out evaluator | "Оценочные данные, которых LLM никогда не видела" | Входы, генерируемые во время оценки, чтобы предотвратить memorization |
