# A2A — протокол Agent-to-Agent

> MCP — это agent-to-tool. A2A (Agent2Agent) — это agent-to-agent: открытый протокол, который позволяет непрозрачным агентам, построенным на разных фреймворках, сотрудничать друг с другом. Выпущен Google в апреле 2025 года, передан Linux Foundation в июне 2025 года, достиг v1.0 в апреле 2026 года при поддержке 150+ участников, включая AWS, Cisco, Microsoft, Salesforce, SAP и ServiceNow. Он вобрал в себя IBM ACP и добавил расширение AP2 для платежей. В этом уроке разбираются Agent Card, жизненный цикл Task и две транспортные привязки.

**Тип:** Сборка
**Языки:** Python (stdlib, Agent Card + harness для Task)
**Предварительные требования:** Фаза 13 · 06 (основы MCP), Фаза 13 · 08 (клиент MCP)
**Время:** ~75 минут

## Цели обучения

- Отличать сценарии agent-to-tool (MCP) от agent-to-agent (A2A).
- Публиковать Agent Card по адресу `/.well-known/agent.json` с навыками и метаданными endpoint.
- Проследить жизненный цикл Task (submitted → working → input-required → completed / failed / canceled / rejected).
- Использовать Messages с Parts (text, file, data) и Artifacts в качестве выходов.

## Проблема

Агент клиентской поддержки должен делегировать написание отчета специализированному агенту-писателю. Варианты до A2A:

- Пользовательский REST API. Работает, но каждая пара интегрируется отдельно.
- Общая кодовая база. Требует, чтобы два агента работали на одном и том же фреймворке.
- MCP. Не подходит: MCP предназначен для вызова инструментов, а не для сотрудничества двух агентов с сохранением непрозрачности внутреннего рассуждения каждого агента.

A2A закрывает этот пробел. Он моделирует взаимодействие как отправку Task одним агентом другому, с жизненным циклом, сообщениями и артефактами. Внутреннее состояние вызываемого агента остается непрозрачным — вызывающий видит только переходы состояния задачи и итоговые выходы.

A2A — это протокол, который "позволяет агентам на разных фреймворках разговаривать друг с другом". Он не заменяет MCP; эти два протокола дополняют друг друга.

## Концепция

### Agent Card

Каждый A2A-совместимый агент публикует карточку по адресу `/.well-known/agent.json`:

```json
{
  "schemaVersion": "1.0",
  "name": "research-agent",
  "description": "Summarizes academic papers and drafts citations.",
  "url": "https://research.example.com/a2a",
  "version": "1.2.0",
  "skills": [
    {
      "id": "summarize_paper",
      "name": "Summarize a paper",
      "description": "Read a paper PDF and produce a 3-paragraph summary.",
      "inputModes": ["text", "file"],
      "outputModes": ["text", "artifact"]
    }
  ],
  "capabilities": {"streaming": true, "pushNotifications": true}
}
```

Обнаружение основано на URL: получить карточку, узнать URL A2A endpoint, перечислить skills.

### Подписанные Agent Cards (AP2)

Расширение AP2 (сентябрь 2025 года) добавляет криптографические подписи к Agent Cards. Издатель подписывает собственную карточку с помощью JWT; потребители проверяют подпись. Это предотвращает подмену личности.

### Жизненный цикл Task

```
submitted -> working -> completed | failed | canceled | rejected
             -> input_required -> working (loop via message)
```

Клиенты инициируют задачу через `tasks/send`. Вызываемый агент проходит через состояния; клиенты подписываются на обновления состояния через SSE или опрашивают их.

### Messages и Parts

Сообщение несет одну или несколько Parts:

- `text` — обычное содержимое.
- `file` — base64 blob с mimeType.
- `data` — типизированная JSON-нагрузка (структурированный вход для вызываемого агента).

Пример:

```json
{
  "role": "user",
  "parts": [
    {"type": "text", "text": "Summarize this paper."},
    {"type": "file", "file": {"name": "paper.pdf", "mimeType": "application/pdf", "bytes": "..."}},
    {"type": "data", "data": {"targetLength": "3 paragraphs"}}
  ]
}
```

### Artifacts

Выходы — это Artifacts, а не сырые строки. Artifact — именованный типизированный выход:

```json
{
  "name": "summary",
  "parts": [{"type": "text", "text": "..."}],
  "mimeType": "text/markdown"
}
```

Artifacts могут передаваться потоково как фрагменты. Вызывающий агент накапливает их.

### Две транспортные привязки

1. **JSON-RPC over HTTP.** Endpoint `/a2a`, POST для запросов, опционально SSE для streaming. Привязка по умолчанию.
2. **gRPC.** Для корпоративных сред, где gRPC является нативным.

Обе привязки переносят одну и ту же логическую форму сообщения.

### Сохранение непрозрачности

Ключевой принцип дизайна: внутреннее состояние вызываемого агента непрозрачно. Вызывающий видит состояние задачи и артефакты. Chain-of-thought вызываемого агента, его вызовы инструментов, его делегирование субагентам — все это невидимо. Это отличается от MCP, где вызовы инструментов прозрачны.

Обоснование: A2A позволяет конкурентам сотрудничать без раскрытия внутренней реализации. A2A может быть "вызови этого агента клиентской поддержки" без того, чтобы вызывающий узнал, как этот агент реализует сервис.

### Связь с MCP

| Измерение | MCP | A2A |
|-----------|-----|-----|
| Сценарий | Agent-to-tool | Agent-to-agent |
| Непрозрачность | Прозрачные вызовы инструментов | Непрозрачное внутреннее рассуждение |
| Типичный вызывающий | Agent runtime | Другой агент |
| Состояние | Результат вызова инструмента | Task с жизненным циклом |
| Авторизация | OAuth 2.1 (Фаза 13 · 16) | JWT-подписанные Agent Cards (AP2) |
| Транспорт | Stdio / Streamable HTTP | JSON-RPC over HTTP / gRPC |

Используйте MCP, когда нужно вызвать конкретный инструмент. Используйте A2A, когда нужно делегировать целую задачу другому агенту. Многие production-системы используют оба: агент использует MCP для слоя инструментов и A2A для слоя сотрудничества.

## Используйте

`code/main.py` реализует минимальный harness A2A: research agent публикует свою карточку, writer agent получает `tasks/send` с parts, включая PDF и текстовую инструкцию, проходит через working → input_required → working → completed и возвращает текстовый artifact. Все на stdlib; используется in-memory транспорт, чтобы сфокусироваться на формах сообщений.

На что обратить внимание:

- JSON-форма Agent Card.
- Назначение Task id и переходы состояний.
- Messages с parts смешанных типов.
- Ветка input-required в середине задачи.
- Возврат Artifact при завершении.

## Отгрузите

Этот урок создает `outputs/skill-a2a-agent-spec.md`. Для нового агента, который должен вызываться другими агентами, skill создает JSON Agent Card, схему skills и blueprint endpoint.

## Упражнения

1. Запустите `code/main.py`. Проследите полный жизненный цикл Task, включая паузу input-required, где вызываемый агент просит уточнение.

2. Добавьте подписанную Agent Card. Подпишите HMAC поверх канонического JSON карточки. Напишите verifier и подтвердите, что он падает на измененной карточке.

3. Реализуйте task streaming: writer agent отправляет три инкрементальных фрагмента artifact через SSE, а вызывающий агент накапливает их.

4. Спроектируйте A2A agent, который оборачивает MCP server. Сопоставьте каждый MCP tool с A2A skill. Отметьте trade-offs — какая непрозрачность теряется?

5. Прочитайте анонс A2A v1.0 и определите одну функцию, которая по состоянию на апрель 2026 года еще не реализована ни одним фреймворком. (Подсказка: она связана с многошаговым делегированием задач.)

## Ключевые термины

| Термин | Как говорят | Что это на самом деле означает |
|------|----------------|------------------------|
| A2A | "Протокол Agent-to-Agent" | Открытый протокол для непрозрачного сотрудничества агентов |
| Agent Card | "`.well-known/agent.json`" | Опубликованные метаданные, описывающие навыки агента и endpoint |
| Skill | "Вызываемая единица" | Именованная операция, которую поддерживает агент (аналог MCP tool) |
| Task | "Единица делегирования" | Рабочий элемент с жизненным циклом и финальным artifact |
| Message | "Вход Task" | Несет Parts (text, file, data) |
| Part | "Типизированный фрагмент" | Элемент сообщения `text` / `file` / `data` |
| Artifact | "Выход Task" | Именованный типизированный выход, возвращаемый при завершении |
| AP2 | "Agent Payments Protocol" | Расширение Signed Agent Cards для доверия и платежей |
| Opacity | "Сотрудничество как с черным ящиком" | Внутренности вызываемого агента скрыты от вызывающего |
| Input-required | "Пауза Task" | Состояние жизненного цикла, когда агенту нужна дополнительная информация |
